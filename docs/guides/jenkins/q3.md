# Multibranch Pipelines, Webhooks and Source Trust

> **Engineering scenario:** Onboard a repository with feature branches and external pull requests. How do Jenkins branch indexing, webhook triggers, credentials and PR trust rules interact, and how do you prevent an unreviewed fork from publishing to production?

## The three distinct operations

**Discovery** finds repositories, branches and change requests through a configured SCM source. **Triggering** reacts to a webhook or a scheduled scan and schedules builds. **Checkout** retrieves the code revision or merge result used by the Pipeline. They can fail independently: a webhook can arrive even when a job lacks SCM permission, and a branch can be indexed without a build being authorized to deploy.

```mermaid
sequenceDiagram
 participant S as Git hosting
 participant W as Webhook endpoint
 participant C as Jenkins SCM source
 participant B as Multibranch job
 participant A as Isolated agent
 S->>W: Signed event about branch/PR
 W->>C: Deliver event
 C->>S: Query repository, ref and metadata
 C->>B: Discover or update branch job
 B->>B: Apply trust and build policies
 B->>A: Checkout selected commit / merge revision
 A->>A: Run permitted PR checks
 A-->>B: Test result and commit status
 ```

Configure webhook authentication/signature verification where the corresponding plugin supports it, maintain least-privileged SCM access, and avoid making scheduled full scans the sole reliability mechanism. Event delivery may be duplicated or delayed. Build exactly the intended SCM revision and show it in the build metadata; moving branch tips should not change an already-approved artifact.

## Trust boundary: Jenkinsfile versus submitted code

A fork contributor can modify both source and Jenkinsfile. Plugins providing Multibranch or Organization Folder support implement trust policies that can select a **trusted Jenkinsfile** while testing untrusted code, but the precise behavior depends on SCM source plugin and its version. A trusted Jenkinsfile doesn't make executing attacker-controlled tests safe when its agent has release secrets.

```mermaid
flowchart TD
 EVENT["Branch / change request detected"] --> CLASS{"Source trusted?"}
 CLASS -->|Untrusted| CHECK["Restricted, no-secret build"]
 CLASS -->|Trusted| MAIN["Normal validation"]
 CHECK --> TEST["Build/test with isolated credentials"]
 MAIN --> TEST
 TEST --> RESULT["Immutable result for specific commit"]
 RESULT --> GATE{"Protected branch and authorization?"}
 GATE -->|No| END["Report check result only"]
 GATE -->|Yes| RELEASE["Separate trusted promotion"]
 ```

### Example conditions

```groovy
pipeline {
  agent { label 'pr-sandbox' }
  stages {
    stage('Test source') {
      steps {
        checkout scm
        sh './scripts/test.sh'
      }
    }
    stage('Describe release eligibility') {
      when {
        allOf {
          branch 'main'
          not { changeRequest() }
        }
      }
      steps {
        echo 'Eligible to request a separately authorized release'
      }
    }
  }
}
```

**Important:** `branch 'main'` and `changeRequest()` are not security controls by themselves; anyone who can configure Pipeline steps on an agent holding credentials can abuse those credentials. Release must be a separate constrained identity and policy boundary.

## Why Organization Folder credentials need special care

One broad SCM scan credential can unintentionally reach several private repositories. Users able to influence Jenkinsfile content may be able to abuse capabilities exposed by the organization's jobs. Prefer repository-scoped credentials/Apps, explicit folder separation, reviewed SCM source plugin settings and minimal rights to create/manage webhooks.

## Troubleshooting a missing PR build

1. Was a webhook received and accepted, or was its signature rejected?
2. Did SCM branch indexing recognize the change request?
3. Does the trusted Jenkinsfile path exist and satisfy branch trust settings?
4. Does Jenkins have permission to query that repository/ref?
5. Was the build filtered by branch discovery, build strategy or duplicate event?
6. Is it scheduled but blocked in the build queue, or actually running?

Distinguish **no build scheduled** from **build queued**. Check scan logs before debugging executors.

## Generic incident

A developer forks a public service repo. A misconfigured job allows forks to access the same registry-push credential as the release branch. An attacker can exfiltrate it from a malicious test step despite console masking. Immediate mitigation is credential revocation and trusted-agent isolation, not a superficial change to the Jenkinsfile. Review every dependent job and token scope.

### Spoken explanation

> “I'd separate event delivery, branch discovery and checkout, then review the trust model. Untrusted PRs can run tests only on isolated agents with no release secrets. I'd lock down SCM scanning credentials and treat branch conditions as convenience logic, not authorization. Release promotion needs a protected identity tied to reviewed revisions. When a PR doesn't build, I'd inspect webhook and indexing logs before assuming agent capacity is the problem.”
